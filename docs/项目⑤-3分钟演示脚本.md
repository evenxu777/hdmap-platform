## 1. 一句话

这是一个把矿区/园区矢量地图数据从文件导入数据库、再通过 HTTP 接口和浏览器完成查看、查询与在线编辑的最小平台，默认用 SQLite 单机跑，也可以切到 PostGIS。

给谁用：需要把 Shapefile/GeoJSON 快速变成可浏览、可修改的内部工具的人；不是面向公网的生产地图服务。

## 2. 业务背景

高精地图数据的典型链路是：采集车/作业车产出点云和轨迹 → 内业矢量化成道路、围栏、装卸点等要素 → 质检和编辑 → 发布给业务系统使用。

这个项目只做中间一段：**矢量化成果已经变成 GeoJSON/Shapefile 之后，怎么入库、怎么查、怎么在浏览器里改、怎么以瓦片形式提供给下游**。

没有做采集、点云处理、自动矢量化、路径规划，也没有做审核流。原因是这些环节需要专门的算法和数据，和“数据入库 + 可视化编辑 + 服务发布”是两类问题。

## 3. 架构与数据流

```
数据文件                 存储                     服务                      前端
────────                 ────                     ────                      ────
data/site.geojson  ──▶  SQLite data/map.db    ──▶  GET /api/features   ──▶  OpenLayers 2D
Shapefile          ──▶  PostgreSQL/PostGIS    ──▶  GET /api/tiles/*.pbf    （点选/新增/编辑）
（tools/import_shapes）      features 表           GET /api/stats         Three.js 简易 3D
                                                 PUT /api/features/{id}
```

每一跳的选择和原因：

| 跳 | 技术 | 为什么 |
| --- | --- | --- |
| 文件 → 数据库 | SQLite（标准库）、PostGIS（psycopg2） | SQLite 让项目零配置可跑；PostGIS 提供空间索引、`ST_AsMVT` 和真实的空间查询，二者同一套表结构 |
| 数据库 → 要素接口 | FastAPI + 手写 SQL | 接口量小，直接用 SQL 比引入 ORM 更直观；SQLite 和 PostGIS 各写一份实现，行为对齐 |
| 数据库 → 瓦片 | PostGIS `ST_TileEnvelope` + `ST_AsMVT`；备选 Python `mapbox-vector-tile` | 有 PostGIS 时不把数据拉回 Python；没有 PostGIS 时用 Python 在进程内编码，保证 SQLite 也能出 MVT |
| 要素 → 2D 页面 | OpenLayers 7.5.2 + GeoJSON | 需要点选、绘制、编辑交互，OpenLayers 自带这些能力；全部本地 vendor，断网可用 |
| 要素 → 3D | Three.js r134 | 只是把同一份 GeoJSON 按高度拉伸，Three.js 足够；不需要地形和倾斜摄影引擎 |

请求从进入 FastAPI 到返回会经过：请求 ID 中间件（`ContextVar`）→ 路由 → 参数校验 → SQLite/PostGIS → 指标记录；异常统一转成 `{"error": {...}}`。

## 4. 关键实现与踩过的坑

每条都按“现象 → 根因 → 怎么定位 → 怎么修”讲；这些都是项目里真实发生过的。

### 4.1 页面地图空白，`/api/features` 500（JSONB 被二次 `json.loads`）

- **现象**：浏览器打开后地图只有底图网格，状态栏一直停在“加载中…”，Network 里 `/api/features` 返回 500，`.pbf` 请求数是 0。
- **根因**：`features.props` 在 PostGIS 里是 JSONB，psycopg2 读出来已经是 `dict`；`app._pg_feature()` 里又执行了一次 `json.loads(row["props"])`，抛 `TypeError: the JSON object must be str, bytes or bytearray, not dict`。SQLite 的 `props` 是 TEXT，所以同样的代码在 SQLite 下不会报错。
- **怎么定位**：先用 `curl` 确认 500，再在项目 venv 里直接调用 `db.pg_list_features()` 和 `app._pg_feature()` 拿到完整堆栈；同时对比 SQLite 分支的列类型。浏览器侧用无头 Chrome 的 CDP 确认 `vectorSource.getFeatures().length` 是 0、`/api/features` 是唯一的失败请求。
- **怎么修**：在 `_pg_feature()` 里判断类型，`str` 才 `json.loads`，`dict` 直接使用：

```python
props = row["props"] or {}
if isinstance(props, str):
    props = json.loads(props)
props = dict(props)
```

- **附带结论**：页面根本没有 `ol.source.VectorTile`，所以“瓦片加载不出来”是误判；查空白页要先看 `/api/features`，不要先怀疑瓦片。

### 4.2 `ST_AsMVT` 正常但接口 500（`memoryview` 不是 `bytes`）

- **现象**：PostGIS 分支的瓦片 SQL 单独执行有结果，走接口却 500。
- **根因**：psycopg2 把 `bytea` 返回成 `memoryview`，Starlette 的 `Response(content=...)` 只接受 `bytes`。
- **定位**：在 `pg_tile_mvt()` 里打印返回类型；SQL 结果非空但类型不是 `bytes`。
- **修复**：`return bytes(row[0])`。响应头仍标 `X-Tile-Source: postgis-st_asmvt`，便于确认走的是哪条路径。

### 4.3 本机 GDAL 没有 PostgreSQL 驱动，改走 PGDUMP

- **现象**：`ogr2ogr -f PostgreSQL PG:"..."` 报找不到 PostgreSQL 驱动；`ogrinfo --formats` 里只有 `PGDUMP`。
- **根因**：本机 GDAL 3.9.2 的编译选项没有包含 PostgreSQL 客户端驱动，不是 DSN 写错。
- **定位**：先看 `ogr2ogr --formats`，再用 `ogrinfo` 验证 Shapefile 能读；确认是驱动缺失而不是连接问题。
- **修复**：改用 `ogr2ogr -f PGDUMP` 生成 SQL，再用 psycopg2 执行到 `staging`。这样不引入 GDAL Python 绑定，也不改变运行依赖。

### 4.4 每份 PGDUMP 都带 `CREATE SCHEMA`，第二次执行报错

- **现象**：第二次导入时提示 schema `staging` 已存在。
- **根因**：PGDUMP 每份文件开头都自带 `CREATE SCHEMA staging`，而脚本在建 staging 时已经创建过一次。
- **修复**：`run_sql_file()` 逐行过滤掉 `CREATE SCHEMA` 语句；schema 的生命周期由脚本统一管理（开始时 `DROP ... CASCADE` 再 `CREATE`）。

### 4.5 DBF 字段名只有 10 个字符

- **现象**：`capacity_tph` 这类字段在 DBF 里被截断成 `capacity_1`，含义丢失。
- **根因**：DBF 格式的字段名上限是 10 个字符。
- **修复**：只把常用短字段映射成数据库列，完整属性写进 `props_json`，合并时转成 JSONB 的 `props`；单个属性值限制在 80 字符以内，避免脏数据撑爆列。

### 4.6 重复导入导致数据翻倍，改成 `shape_key` 幂等

- **现象**：第一次导入后总数从 9 变成 18；再跑一次又加 9 条。
- **根因**：合并阶段是纯 `INSERT`，没有唯一约束；示例 GeoJSON 和由它派生的 Shapefile 本来就是同一批数据。
- **修复**：拆分时给每条记录生成稳定的 `shape_key`（如 `sf-point-04`），合并 SQL 带 `WHERE NOT EXISTS (... f.props->>'shape_key' = s.shape_key)`。staging 每次重建，`features` 不重复。
- **验证**：第一次 18 条（种子 9 + Shapefile 9），第二次新增 0。要回到 9 条，删除 `props->>'src' = 'shapefile'` 的记录即可。

### 4.7 编辑冲突：`version` 乐观锁返回 409

- **现象**：两个页面同时改同一条点位，后保存的会覆盖先保存的。
- **根因**：更新语句只按 `id` 匹配，没有并发控制。
- **修复**：每条记录带 `version`。更新 SQL 是 `UPDATE ... WHERE id=? AND version=? RETURNING version`，命中则 `version+1`，0 行返回 `None`，接口转成 409 `VERSION_CONFLICT`，并把 `your_version` 放进 `details`。前端保存时带上打开面板时拿到的 `version`，失败时直接显示错误。
- **边界**：只保证“不会静默覆盖”，没有自动重试和字段级合并。

### 4.8 请求 ID 用 `ContextVar` 贯穿日志和错误体

- **现象**：出错时终端日志和响应体里的 `request_id` 对不上，排查要来回拼。
- **根因**：日志、异常处理、响应构造是三个位置，没有共享上下文。
- **修复**：中间件里生成（或沿用请求头里的）ID，写入 `ContextVar`；日志过滤器、`error_body()`、响应头都读同一个值。前端展示 `request_id`，用户报错时可以直接定位到那一条日志。

### 4.9 PostGIS 启动报 `OperationalError: <empty>`，其实是密码被拒

- **现象**：启动直接退出，报 `[PostGIS 连接失败] ... OperationalError: <empty>`，DSN 解析看起来完全正确。
- **根因**：DSN 里的密码不是 `mapdemo` 的真实密码（常见于环境变量里还留着占位符「你的密码」）。本机 psycopg2 2.9.9 + libpq 16 在“服务器侧拒绝连接”时，`str(e)`、`pgcode`、`diag` 全是空；而“服务未启动/端口错”会给 `Connection refused`，“没提供密码”会给 `fe_sendauth`，都不会是空。
- **怎么定位**：用同一条 DSN 的密码跑 `psql -U postgres -h 127.0.0.1 -d mapdemo -tAc "SELECT 1"`，psql 会直接给出 `password authentication failed`；再用占位符 DSN 调 `db.pg_error_message()`，能逐字符复现同一段空消息。
- **修复**：`pg_error_message()` 增加空消息分支，直接说明“这是服务器侧拒绝”，并打印 `pgcode/diag/pgerror/args`（有就显示，没有就明确说没有）；同时不把 PostGIS 失败静默降级到 SQLite，避免写错库。
- **为什么不做自动回退**：配置了 PostGIS 就说明数据应该在 PostGIS；悄悄写进 SQLite 会让数据分叉，问题更难查。

## 6. 边界与局限

- **前端不消费 MVT**：2D 页面用 GeoJSON，原因是编辑需要 `version` 和完整属性，而当前瓦片只带 `id/kind/name/props`；如果要改成瓦片渲染，编辑前还要再查一次单要素。
- **PostGIS 没有可用兜底**：`ST_AsMVT` 失败后的 Python 分支是按 SQLite 行结构写的，PostGIS 行没有 `minx/maxx`，会先 `KeyError`；这段需要重写，当前如实写成已知限制。
- **SQLite 没有空间索引**：只有 `(minx,miny,maxx,maxy)` 普通联合索引；Python 兜底是“先全取再按 bbox 过滤”，数据量大了会慢。
- **鉴权只有静态令牌**：`X-Edit-Token`，默认 `demo-token` 还写在页面里；没有用户、角色、审计，CORS 是 `*`。
- **并发只做到乐观锁**：不覆盖、不合并；409 之后由人决定怎么处理。
- **3D 是示意级**：多边形按 `height_m` 或默认高度拉伸，围栏默认 6 米，料堆用属性里的 12 米；没有地形、点云、倾斜摄影、3D Tiles。
- **CI 只覆盖 SQLite 测试**：GitHub Actions 在 `push`/`pull_request` 时用 Python 3.10 跑 `pytest`；PostGIS 与需要 Chrome 的 `verify_*.py` 仍是本地手动执行。仓库有 `Dockerfile` 和 `docker-compose.yml`，但本机没有 Docker，未实际构建验证。
- **PostGIS 只在本机单实例验证**：PostgreSQL 17 + PostGIS 3.6，库名 `mapdemo`；没有连接池、主从、容量规划。
- **导入限制**：只接受 SRID 4326、几何非空的 Shapefile；DBF 字段名 10 字符截断；不支持多图层和批量大文件。

为什么没做：这个项目的目标是先把“入库 → 查询 → 编辑 → 发布”跑通，上述能力需要额外的数据、基础设施或团队协作，硬做只会得到不可信的结果。

## 8. 预设追问 Q&A

### Q1：为什么不用 Mapbox GL JS，而用 OpenLayers？

Mapbox GL 需要 access token，样式和底图默认走在线服务，离线部署要额外处理；这个项目要求断网可开。OpenLayers 是本地 vendor 的单文件库，点选、绘制、修改这些交互直接可用，和 GeoJSON 的配合也简单。代价是 3D 要另接 Three.js，生态没有 Mapbox 那么一体化。

### Q2：为什么 3D 不用 Cesium？

Cesium 适合地球尺度、地形、3D Tiles、倾斜摄影；这个项目只有一份 2D GeoJSON，3D 只是按高度拉伸体块。上 Cesium 会增加体积和坐标系/相机复杂度，收益为零。如果以后接入点云或倾斜摄影，再评估 Cesium 或 3D Tiles。

### Q3：MVT 和 GeoJSON 为什么同时存在？

职责不同：GeoJSON 带完整属性和 `version`，用于编辑和属性面板；MVT 是给下游或大范围浏览的发布格式，体积小、按瓦片取。当前前端用 GeoJSON，MVT 只提供接口。如果前端改 MVT，编辑前还需要调用 `GET /api/features/{id}` 拿 `version`，因为瓦片里没有 `version/status/updated_at`。

### Q4：瓦片怎么切？坐标系怎么处理？

XYZ 方案，URL 是 `/api/tiles/{z}/{x}/{y}.pbf`，`z` 限制 0~22。数据存 EPSG:4326；PostGIS 路径先 `ST_TileEnvelope(z,x,y)` 得到 3857 的瓦片范围，再把要素 `ST_Transform` 到 3857，用 `ST_AsMVTGeom(..., 4096, 64, true)` 压到 4096 的瓦片坐标，最后 `ST_AsMVT(..., 'site', 4096, 'geom', 'id')`。Python 路径用球面墨卡托公式算瓦片经纬度范围，再按 4096 的 extent 量化，`y_coord_down=true`，和 MVT 规范一致。没有预切片，都是请求时生成。

### Q5：编辑冲突怎么解决？

乐观锁。每条记录有 `version`；更新 SQL 同时匹配 `id` 和 `version`，成功后 `version+1`，匹配不到返回 409 `VERSION_CONFLICT`。前端把打开面板时的 `version` 带回服务端，冲突时显示错误和 `request_id`。没有自动合并或重试，需要人判断保留哪一版。

### Q6：数据量大了会怎样？

PostGIS 路径有 GiST 索引，`ST_AsMVT` 在数据库里完成，主要瓶颈会变成瓦片生成和重复计算；SQLite 路径目前是“先全表取出再按 bbox 过滤”，属于 O(n)，几万条以后会明显慢。下一步应该做：bbox 条件下推到 SQL、加瓦片缓存/预切片、几何简化、连接池；再往上才考虑分表或对象存储。

### Q7：如果让你重做，会改哪里？

优先四件事：一是配置和启动校验集中管理，环境变量缺项在启动时就报清楚；二是 PostGIS 连接池和迁移脚本，不靠 `CREATE TABLE IF NOT EXISTS`；三是把读写路径拆开，瓦片和要素接口分别限流、分别缓存；四是补 PostGIS 的集成测试和 CI。前端如果还要继续做，会把 MVT 渲染和编辑分开：MVT 负责看，单要素接口负责改。

### Q8：为什么 PostGIS 连不上不自动回退 SQLite？

因为配置了 `DATABASE_URL` 就表示数据应该在 PostGIS。自动回退会让服务看起来正常，实际把数据写进了另一个库，后面很难发现。现在的行为是启动失败、打印 DSN 的 host/port/dbname/user（隐藏密码）和底层异常，让人先修连接。

### Q9：权限和安全怎么考虑？

现在只有一个静态 `X-Edit-Token`，默认值写在页面里；没有用户身份、角色、审计，CORS 是 `*`，也没有 TLS。它只适合本机或可信内网。要上线至少需要 JWT/会话、写操作鉴权、CORS 白名单、速率限制和操作日志。

### Q10：Shapefile 入库为什么要绕 Shapefile → PGDUMP → staging，不直接写库？

因为本机 GDAL 没有 PostgreSQL 驱动，`ogr2ogr -f PostgreSQL` 用不了。用 PGDUMP 生成 SQL 再执行，不需要引入 GDAL Python 绑定。staging 这层的作用是先把字段、SRID、空几何检查完，再按 `shape_key` 合并，失败不会污染 `features`。

### Q11：怎么证明这些功能真的能用，而不是只写了代码？

三层：`pytest -q` 覆盖 SQLite 的接口行为（当前 12 个通过，已接入 GitHub Actions）；`tools/verify_pg.py` 直接请求 PostGIS 的健康检查、要素、瓦片；`tools/verify_offline.py` 和 `tools/verify_edit.py` 用无头 Chrome 打开真实页面，检查要素数、编辑后 `version` 递增、外部请求数。后两者和 PostGIS 检查不在 CI 里，是本地手动跑，结果按日期记在文档里。

### Q12：为什么页面不用 MVT，却还要做瓦片接口？

瓦片是发布能力，面向的是下游地图客户端或后续的大范围浏览；当前页面的核心是编辑，GeoJSON 更方便。两套接口共用同一张 `features` 表，不存在两份数据。这个取舍如实写在 README 的“已知限制”里，不把它说成“前端已经瓦片化”。

## 9. 容易说错的点

- 不要说用过 Tippecanoe，也不要说“5 秒变 25 毫秒”；项目里没有这段实现和测量。
- 不要说“CI 覆盖了 PostGIS/浏览器验证”；CI 只跑 SQLite 的 `pytest`。也不要说“Docker 构建通过”，本机没验证。
- 不要说“高并发”“QPS”“瓦片毫秒级”；没有压测数据。
- 不要说“前端走 MVT”；页面用的是 GeoJSON。
- 不要说“PostGIS 没实测”；两条路径都实测过，PostGIS 是 PostgreSQL 17 + PostGIS 3.6。
- 不要说“生产可用”；没有鉴权体系、缓存、监控和容量规划。
- 示例数据是自造的模拟数据，不要暗示来自真实矿区或客户。
- 数字只用第 5 节表里的；被问到没有的数据，直接说“没测过”。
